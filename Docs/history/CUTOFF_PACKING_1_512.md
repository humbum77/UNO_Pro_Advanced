# CUTOFF 1..512 — упаковка в .unosyp (находка 2026-09-29)

Источник: сессия Codex от 2026-09-15, не перенесённая в проект.
Формула проверена на 16 реальных захватах из корпуса `E:\unosyp_to_hex`.

**Статус: CONFIRMED на 15 захватах.** Не путать с полем CC 28 в ответе `0x37`.

## Формула

Значение `VALUE` в диапазоне `1…512` разложено по трём байтам **побитово**,
а не как обычное число. `N = VALUE - 1`:

```
byte38 = (N & 0x1F) << 2
byte39 = 0x08 | ((N >> 5) & 0x07)
byte37 = ((N >> 8) & 0x01) << 1
```

Обратное декодирование:

```
N     = (byte38 >> 2) | ((byte39 & 0x07) << 5) | ((byte37 & 0x02) << 7)
VALUE = N + 1
```

Раскладка по битам:

| биты `N` | куда |
|----------|------|
| 0…4 | `byte38` биты 2…6 |
| 5…7 | `byte39` биты 0…2 |
| 8 | `byte37` бит 1 |

`byte39` бит 3 (`0x08`) — постоянный служебный бит в этих тестах.

## Область применения

Байты `37`, `38`, `39` — это **упакованный 7-битный поток файла `.unosyp`**
(смещение от начала файла), а не распакованное состояние на 260 байт.

Это **не** то же самое, что `state_decoder_map.json`, где CC 28 (`F1_CUTOFF`)
лежит по смещениям `[48, 49, 50]` с масками `0x2 / 0x7c / 0x7` и отображается в
128 состояний MIDI CC 0…127. Контейнеры разные, механизмы разные. Приведённая
формула ничего не утверждает о поле CC 28 и не опровергает его.

## Открытый вопрос: нижняя граница

`00 00 08` декодируется как `VALUE = 1`, а не `0`. Значит `raw = 0`
**не подтверждён**: устройство кодирует минимум первым значением диапазона
`1…512`, даже если интерфейс показывает `0%`.

Преобразовывать `0CUT` в `raw = 0` искусственно нельзя.

## Границы проверки

- Имена файлов `0CUT…15CUT` — **номера в серии захватов, а не значения**.
  Соответствие «имя = значение» неверно: `5CUT` даёт 5 случайно, `1CUT` даёт 103.
- Проверено на 16 файлах корпуса `*CUT.hex.plain.txt`; 15 различных значений.
- Предсказанные границы `1, 5, 10, 15, 20, 31, 32, 33, 34, 255, 256, 257, 512`
  присутствуют в корпусе все.
- Формула не применена к коду проекта: изменение декодера не вносилось.
