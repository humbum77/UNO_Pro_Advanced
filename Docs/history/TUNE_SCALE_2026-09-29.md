# TUNE — шкала и кодирование (2026-09-29)

## 1. Что подтверждено оператором

Ручка TUNE работает как в исходном UNO Synth, но диапазон расширен до ±2 октав.
Первые ±100 центов (1 полутон) читаются в центах, остальное — в полутонах.

В автоматизацию TUNE пишется как

```
0; 1c-99c; 1st; 1st1c-1st99c; 2st; 2st1c-2st99c; ... до 24 st
```

и симметрично в отрицательную сторону.

Подсказка из руководства — после того как регулировка ручкой перешла на
полутоны, центы всё ещё доступны через data knob — означает, что шкала
непрерывна в центах, а меняется только её подпись.

## 2. Внесено

- `automation_metadata.tune_label(semitones)` — грамматика подписи прибора.
  Значения приходят в полутонах с двумя знаками, то есть один шаг равен
  одному центу.
- `Parameter` получил поля `formatter` и метод `format(value)`. Остальные
  параметры сохраняют прежнее поведение.
- `TUNE 1/2/3` переведены с `'st'` на `formatter=tune_label`.
- Оси полосы TUNE теперь подписаны `24st / 0 / -24st` вместо `+24 st / 0 / -24 st`.
- Статус TUNE изменён с
  `PARTIAL: hybrid cents/semitone interpolation unknown` на
  `CONFIRMED hybrid cents/semitone scale: ... Automation native byte encoding
  of this scale is NOT yet determined`.
- `tests/test_tune_scale.py` — 9 тестов, включая полную лестницу из 2401
  значения от 0 до 24 полутонов и зеркальную отрицательную сторону.

Полная лестница:

```
0 | 1c .. 99c | 1st | 1st1c .. 1st99c | 2st | 2st1c .. 2st99c | ... | 24st
```

`24st` — вершина диапазона в две октавы, лестница на нём заканчивается.

## 3. Поле состояния: 128 шагов, упаковка нелинейная

Из `state_decoder_map.json` и `wire_0x37_registry`:

| Параметр | CC | wire-смещения | маски | состояний |
|----------|----|---------------|-------|-----------|
| `OSC1_TUNE` | 15 | 28, 29, 30 | `0x60, 0x7F, 0x7F` | 128 |
| `OSC2_TUNE` | 16 | 34, 35, 36 | `0x78, 0x7F, 0x1F` | 128 |
| `OSC3_TUNE` | 17 | 40, 41, 42 | `0x7E, 0x7F, 0x07` | 128 |

Каждое поле — **7-битный CC на 128 состояний**, а не 2401 значение шкалы
TUNE. Упаковка нелинейна: в LUT по `OSC1_TUNE` значение `cc` растёт на 1 до
прибл. 34, дальше шаг по сырым байтам уменьшается.

Значит состояние прибора хранит TUNE грубее, чем автоматизация: состояние —
128 шагов, запись автоматизации — 2 байта.

## 4. Кодирование записи автоматизации

### 4.1 Чтение, проверенное контролем

Значение TUNE в съёмках лежит по файловому смещению **0x01F1** (страница 1,
смещение 196), в 7-битной упаковке младшим байтом первым. **`пара/16` даёт
центы.** Метод проверен на трёх съёмках с известным значением:

| съёмка | подпись файла | байты по 0x01F1 | `пара/16` |
|--------|---------------|------------------|-----------|
| `TUN1S1_99C` | 99c | `30 0C` | 99 ✓ |
| `TUN1S1_1ST` | 1st | `40 0C` | 100 ✓ |
| `TUN1S1_2ST` | 2st | `00 19` | 200 ✓ |

По этому чтению подтверждаются также `1C`=16, `4C`=64, `8C`=128, `16C`=256,
`32C`=512, `50`=800, `1ST`=1600, `2ST`=3200 — все равны `16 × центы`.

Ошибка предыдущей версии этого документа: там результат деления на 16 был
подписан как «полутоны». Правильно — это **центы**.

### 4.2 Проверка вопроса «пишется ли 1st + c»

Оператор приложил `1test\DHK_Y.unosyp` и спросил, пишется ли автоматизация TUNE
внутри первого полутона. Проверено тем же чтением, что и контроль:

| файл | байты по 0x01F1 | `пара/16` | подпись |
|------|------------------|-----------|--------|
| `DHK_Y` | `20 12` | **146** | **`1st46c`** |

**Да, пишется.** В `DHK_Y` по тому же смещению лежит 146 центов, то есть
`1st46c` — значение строго между `1st` и `2st`, в диапазоне
`1st1c`..`1st99c`.

Подтверждающие признаки, что это настоящая запись, а не случайное окно:

- страницы `DHK_Y` длиннее, чем у лестницы: 203/199 против 198/195;
- запись страницы 1 — `01 06 00 00 20 12 00 3B 00 06 02`, то есть **count=6**
  против `01 02` у лестницы: автоматизации втрое больше;
- страницы 2, 3 и 4 несут один и тот же набор значений (59c, 262c, 288c),
  что и есть повтор шага 1 на остальных шагах.

Прочие integral-значения DHK_Y: 8c, 48c, 146c, 256c, 472c на странице 1;
59c, 262c, 288c на страницах 2-4.

Оговорка: у `DHK_Y` шесть записей автоматизации, и без Parameter Selection
нельзя утверждать, что 146c относится к TUNE. Связь вытекает из имени съёмки
(`DHK` — data knob, как в подсказке руководства) и из того, что 146c попадает
в полосу именно шкалы TUNE. Формально это остаётся `DERIVED`, а не
`CONFIRMED`.

### 4.3 Кодек проекта и полоса 1st+c

Кодек TUNE в `uno_step_automation_decoder` — 2 байта, старшим байтом первым,
со знаком, в центах, делёнными на 100. Он круговой на всей лестнице:

| значение | код | | значение | код |
|----------|-----|---|----------|-----|
| 0 | `0000` | | 2st | `00c8` |
| 1c | `0001` | | 12st | `04b0` |
| 99c | `0063` | | 24st | `0960` |
| 1st | `0064` | | -1st | `ff9c` |
| 1st1c | `0065` | | -1st50c | `ff6a` |
| 1st50c | `0096` | | -12st50c | `fb1e` |
| 1st99c | `00c7` | | | |

Полоса `1st1c`..`1st99c` выразима целиком: `0065`..`00c7`. Формат её держит.

### 4.4 Что осталось нерешённым

Чтение из 4.1 подтверждено до **двух полутонов** и дальше ломается:

| подпись | код | `пара/16` | ожидалось |
|---------|-----|-----------|-----------|
| 2ST | `00 19` | 200 | 200 ✓ |
| 3ST | `40 05` | 44 | 300 ✗ |
| 12ST | `00 16` | 176 | 1200 ✗ |
| 24 | `00 0C` | 96 | 2400 ✗ |

Отрицательная сторона немонотонна: `-1C`→4095, `-1st`→4088, `-99`→2527,
`-2ST`→911, `-24`→2575, `-50C`→3311.

Либо точка извлечения верна не для всех съёмок, либо после двух полутонов
формат меняется, а минус пишется иначе. По имеющимся файлам не различить.
**Правило для значений выше двух полутонов не выдвигается.**

### 4.5 Нужен контроль со значением между 1st и 2st

Чтобы закрыть пункт 4.4, нужна съёмка с точно известным значением вроде
`1st50c` **на лейсте TUN**, а не через data knob, плюс `-1st50c`. Тогда будет
видно, совпадает ли оно с `16 × центы`, и чем минус отличается от плюса.

## 6. Что делать нельзя

- Считать `16 × центы` законом кодирования: оно подтверждено только до двух
  полутонов и опровергнуто на `3ST`, `12ST` и `24`.
- Считать поле состояния TUNE носителем шкалы автоматизации: у него 128
  состояний, у шкалы 2401 значение.
- Путать подпись шкалы с байтовым кодированием: раздел 1 закрывает первое,
  раздел 4 пока не закрывает второе.
